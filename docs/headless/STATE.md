# 本地状态与目录适配（基础组件）

当前组件已接入 `once`/`daemon` 双向文件同步。外部调用方通过受控入口提交修改，不直接操作这些底层方法或数据库；认证成功不代表同步完成。

## 事务存储

`src/headless/state_store.ts` 使用项目固定 Node.js `v24.14.0` 的内置 `node:sqlite`，没有新增 npm 驱动依赖。[该版本官方文档](https://nodejs.org/download/release/v24.14.0/docs/api/sqlite.html) 将此模块标为开发中，运行时会输出 ExperimentalWarning；升级 Node 前必须重跑恢复测试。

格式版本为 `1`，数据库携带专用 application ID。操作、共同基线、批次、会话、本地落盘和冲突记录均有格式版本、修订号、严格字段校验与 SHA-256 校验。记录只存外置快照引用，不存令牌或正文。身份绑定和上传确认组件见下文；完整文件轮次通过独立 `cycle` 检查点确认，不能手改 acknowledged 作为同步证据。

创建必须显式指定；已有空文件、损坏数据库、未知格式或损坏记录均拒绝打开，不能重新初始化。批量提交使用 `BEGIN IMMEDIATE` 和修订号前置条件；任一条失败则回滚全部记录。采用 `DELETE` 回滚日志及 `synchronous=FULL`，创建时同步父目录，快照字节不放进数据库。

当前硬上限：单记录 128 KiB、单事务 1000 条修改、5 万条记录、元数据载荷合计 64 MiB、单次列表最多 1000 条。此为基础组件上限，完整运行资源验收尚未完成。存储故障返回不含路径或 SQL 的错误码。

## 身份绑定与不可变上传组件

`IdentityBinding` 持久化端点、认证主体、Vault 名称、本地目录路径/设备/inode，以及上游可取得的可选服务/Vault ID。不可取得的独立标识显式为 `null`，不伪造身份，也不要求修改上游。启动及重连核对已取得的绑定，认证失败、已知错配或同路径目录替换拒绝恢复；令牌不写入绑定。已有数据但没有绑定的旧状态拒绝自动认领。相同地址、主体标识和 Vault 名称背后的后端替换不在可保证识别范围。

`DurableOutbox` 保存不可变目标快照、预期远端版本、基线和操作顺序。`sent` 提交连接代次与请求 context 后才允许网络发送；同路径或重命名来源/目标相交的后继操作等待前驱确认。确认提交原子更新操作与对应发送版本的基线，不读取后来变更的本地文件。重命名确认还必须提供来源确实不存在的读回证据。

`uploadOperation` 使用共享 `noteModification`、`fileUploadCheck` 和附件帧编码。每个所有者一次只运行一个上传，每次连接只发送一个操作；Ack 必须匹配该连接的路径和可用 context，之后以完整读回版本确认。确认丢失后先读回，目标已存在则恢复基线而不重复发送。附件中断后重建会话、从快照完整重传，不信任旧分片偏移。笔记最大 20 MiB，附件最大 32 MiB，单分片最大 8 MiB，默认期限 60 秒、最大 300 秒。

远端操作遵循官方协议，缺少原子 CAS 不再作为发送门禁；删除与重命名使用共享 `pathMutation` / `renameMutation`，不新增服务端字段。已观察到版本变化仍保留意图并返回冲突；预读之后的竞争是上游继承限制。`test:sync` 覆盖身份变化、后继编辑、重复/错序/旧连接确认、确认丢失重启读回、实际持久化失败、空附件、取消重传和删除/重命名确认丢失。实际 3.5.1 / 3.6.1 的 JSON/protobuf 上传及路径操作也通过；这些组件已接入双向 CLI；整轮验证见 `test:sync` 和固定服务端 `--reconcile` 探针。

`test:state` 已覆盖实际目录权限导致的写入失败、跨记录回滚、修订号冲突、重启、提交后 SIGKILL、未提交事务 SIGKILL、未知版本与损坏记录不被改写。文件快照与替换边界另由下述 `test:application` 验证。

## Linux 目录适配

`src/headless/filesystem.ts` 当前提供 Linux/WSL 适配；用户已确认首版目标为 Linux / Linux 容器（含 WSL）。其它系统显式返回 `unsupported-platform`。Linux 需可用的 `/proc/self/fd` 与 `/usr/bin/flock`。当前允许 ext4、tmpfs、btrfs、XFS、overlay 类型的本地文件系统；其它类型拒绝启动，网络共享与跨主机锁未获验证。

Vault 和外置状态目录必须预先存在、为不含符号链接的规范绝对路径，不能相同或互相包含。目录身份记录路径、设备和 inode；同路径目录被替换时拒绝继续。读取和写入逐级打开目录描述符，使用 `O_NOFOLLOW`，拒绝符号链接、硬链接、特殊文件、父目录逃逸及大小写/Unicode 规范化碰撞。写入使用同目录临时文件，创建使用不覆盖目标的原子链接，替换使用原子重命名；这些底层方法仍须由后续持久恢复意图和版本互斥层调用。

所有权直接锁定两个目录 inode；临时 `flock` 子进程继承描述符，锁在主进程持有描述符期间持续有效，进程退出自动释放。该行为依据 [Linux flock 文档](https://man7.org/linux/man-pages/man2/flock.2.html)，并已用独立进程验证。同一 Vault 即使指定不同状态目录也被拒绝，不使用超时删除 PID 文件来抢锁。`flock` 是协作锁，不能替代 Ops 对外部 Bot 的直接写入权限限制。

适配器当前限制单文件 128 MiB、每层目录 5 万个名称、相对路径最多 64 层。`.fns-headless-` 前缀保留给临时文件，业务路径拒绝使用，普通枚举排除该前缀。临时资料恢复/清理和配额仍属于后续任务；不能将遗留临时文件当作同步内容。

`test:filesystem` 已覆盖两个独立进程争夺相同 Vault/状态目录、SIGKILL 后释放、路径逃逸、符号链接替换确定性时序、硬链接、大小写与 Unicode 碰撞、临时写入失败不发布半文件、同路径目录替换。它不证明任意不受控外部写入者的并发安全。

## 外置快照和文件恢复

`SnapshotStore` 将完整内容放在外置状态目录的 `snapshots/<sha256>`，数据库只保存引用。调用前复制输入，避免异步哈希期间调用方改变缓冲区；线上协议哈希仍使用共享上游算法。读取快照核对完整 SHA-256 与长度，损坏或丢失明确失败；未知编码的笔记拒绝按替换字符转码，二进制仍按原字节保存。

`FileApplication.prepare` 在同一所有者互斥范围内核对预期完整版本，持久化原版本/目标快照，再提交 prepared 记录；此时尚未改动 Vault。`apply` 再次核对当前完整内容：原版本仍在则原子写入，已是目标版本则补齐本地提交，出现其它版本则保留该版本快照并记为 diverged。缺少写入方式声明时拒绝构造文件应用入口；这仍不替代 Ops 的实际权限验收。

新文件采用硬链接进行原子、不覆盖目标的发布。如果在链接成功、临时名称移除前崩溃，恢复仅移除已验证为同目录、同 inode 的唯一保留前缀临时别名，要求总链接数恰为 2；保留目标字节，再核对完整版本。任意外部硬链接仍拒绝。替换操作未发布的遗留临时文件继续被排除同步，自动回收和总空间配额待资源里程碑完成。

`test:application` 对创建/替换各执行 prepare 后、临时文件写入后、发布后、状态提交后的 SIGKILL，共 8 个标准崩溃窗口；另验证创建/替换发布后被外部修改、真实状态提交权限失败、损坏/丢失快照以及幂等重试。恢复保留原内容、目标内容与外部修改；本地 applied 回执不会创建同步基线或推进网络批次。

## 最小冲突记录

`ConflictStore.capture` 在同一所有者互斥范围内保存本地、远端和可用共同基线的快照。`baseStatus` 明确区分 `missing`（无历史）、`absent`（基线确认不存在）和 `present`。首次同路径内容不同保留双方，记录为 open，不按时间戳覆盖、不自动选取胜者。

`test:conflicts` 覆盖首次接入、三方版本、删除对修改、二进制内容、重启，以及非法/丢失快照引用。当前只有冲突保存与读取；决策 schema、幂等提交、远端复核、Hermes 馆长接入和已解决状态均未实现，不能据此宣称通用冲突解决接口完成。

## 受控本地入口

`startLocalRuntime` 启动仅处理本地请求的所有者服务；不连接远端，不是双向同步 CLI。启动必须声明 `controlled` 或 `exclusive`，缺失时在打开状态前拒绝，Vault 和状态目录零副作用。目录须预先存在，状态目录权限为 `0700`。辅助进程通过状态目录的 `control.sock` 向所有者提交 JSON 请求；socket 权限为 `0600`，最多 4 个连接、单请求 16 MiB，内容使用标准 Base64。该权限允许同用户调用；Hermes Ops 须提供受限调用桥接并验证 Bot 无直接 Vault 写权限，配置声明和本仓库测试不能替代此验证。

请求信封为 `schemaVersion: 1`、`action: "local-write"` 和 `request`。请求包含 `requestId`、`operation`（`create`、`modify`、`delete`、`rename`）、`path`、`contentKind`（`note` 或 `file`）和 `expected`（完整 `sha256`/`size`，创建必须为 `null`）。创建/修改另需 `contentBase64`；重命名另需 `targetPath` 及 `targetExpected: null`，不覆盖已有目标。父目录当前须预先存在。正文和路径只经受控接口与存储传递，不写普通日志。

同一 ID 的相同载荷返回原回执，JSON 字段顺序不影响幂等；不同载荷返回 `request-id-reused`。陈旧请求持久化为 `stale`，保留提交内容快照。`applied` 只说明本地操作提交，所有回执均带 `synchronization: "not-confirmed"`，不会生成已确认共同基线。

删除先原子移到同目录 `.fns-headless-delete-<fingerprint>`，提交后才清理；此保留位置在崩溃窗口固定原 inode，防止原路径重建同内容文件或 inode 复用导致重复删除。重命名恢复同时核对来源、目标 inode 和完整内容；存在新来源或占用目标时保留内容、返回陈旧状态。已提交的重复请求不会再次执行文件操作。

`test:local` 使用独立所有者与 Bot 进程，在版本复核后、实际替换前设置确定性屏障，覆盖远端先应用、Bot 先应用、竞争重命名目标；另覆盖删除/重命名三个提交边界及同内容后继文件共 12 个 SIGKILL 场景，以及启动门禁、socket 权限和重启幂等。冲突决策尚未实现，因此任务 2.9 的完整三入口互斥验收仍未完成。

## 整轮同步和恢复

`reconcile` 记录在远端内容本地应用前保存原版本/目标版本；应用成功后与共同基线提交。重启补完本地回执，不覆盖应用后的后继编辑。远端清单中缺失但没有回收站历史的项目记为 `historyUnverified`，不据此删除本地文件。`cycle/latest` 只在所有已观察文件版本一致、没有冲突/pending/历史疑问时提交。最后完整扫描与检查点提交共用所有者互斥，已排队的 Bot 修改只能在之前或之后执行。

运行时先验证认证身份，再恢复本地请求和同步意图；恢复失败不清理旧状态。`status` 返回计数和上次完成时间，不返回路径/正文，也不把旧检查点称为当前实时一致。

## 冲突决定与恢复

`decision` 记录持久化幂等标识、指纹、冲突引用、决定、目标快照和处理状态。`prepared` 决策必须在所有者互斥内复核完整本地/远端版本，随后提交带 `decisionId` 的本地意图；这些意图不会被普通请求恢复直接执行。`applied` 仍未确认远端，上传确认与精确读回完成后才提交 `confirmed` 并将冲突标为 `resolved`。被明确决策取代的旧上传意图标记 `cancelled`，保留快照，不伪造 acknowledged。

陈旧决策生成稳定 ID 的新冲突，旧记录 `superseded`，决策 `stale` 并关联下一冲突。即使生成新冲突后的终态提交失败，重启也不会让旧决定重新有效。新冲突可能带 `reason: versions-changed`；即使当前双方已恰好相同，旧合并决定也失效，需要针对新版本确认。受控查询、分块快照和决定例子见 [CONTROL.md](CONTROL.md)。

新客户端会保留可读取的旧元数据；更旧镜像不认识新增记录/状态时会拒绝打开。回滚应停写并恢复匹配版本的状态备份，不将较新数据库直接交给只读预览或旧镜像，也不通过手改格式号绕过检查。
