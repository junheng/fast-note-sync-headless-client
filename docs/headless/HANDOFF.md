# Fast Note Sync Headless Client 实现交接

## 1. 任务与当前状态

用户决定维护官方插件的 fork，将项目定义为 **Fast Note Sync Headless Client**，后续 Agent 在本仓库继续实现。目标是让 Obsidian 与 Bot 的笔记修改双向同步；发生冲突时，Hermes 的“智库馆长”必须负责解决。

当前已有独立 Node `once`/`daemon` 双向文件同步与持久恢复入口，保留原插件构建。原版 3.5.1/3.6.1 的笔记、9 MiB 附件、离线删除、受控重命名（含大小写重命名）、独立 CLI 与重启验证通过；版本化冲突决策已接入并经真实服务端验证；空目录的官方 `FolderSync*` 通道、实际 Obsidian 操作矩阵和 Hermes 业务验收尚未完成。Docker 与具体支持边界见 [DOCKER.md](DOCKER.md)，实际验证见 [VALIDATION.md](VALIDATION.md)。历史方案段落不能替代 OpenSpec 任务的当前状态。

后续实施已按用户要求切换为正式稳定版 `2.4.0`（`f2b15c09`），工作分支为 `headless/stable-2.4.0`。原 `1bfb4069` 开发分支提交的验证记录仅作历史证据，不能替代稳定版基线；具体结果和修复状态以验证记录及 OpenSpec 任务为准。

用户随后决定暂不处理上游大附件采样盲区，等待上游修复。该问题保留为首版已知限制，专项任务延后，不再阻塞其余实施；详见 `SERVER-CAPABILITIES.md` 和 OpenSpec 延后清单。此例外不取消其他操作确认、冲突及持久化要求。

## 2. 排查背景与证据边界

此前第三方 Python CLI 的现网实现存在本地保护补丁阻断附件/配置拉取的问题；更早的同步失败不能仅凭该补丁归因。比对源码还发现大文件哈希、Unicode 字符串哈希、上传消息结构及批次完成判断的兼容性问题。继续修补该 CLI 容易形成第二套长期追赶官方协议的实现，因此转向复用官方 TypeScript 代码。

已观察到的官方实现：

- `src/lib/utils/helpers.ts`：字符串按 JavaScript UTF-16 单元计算哈希；大于 10 MiB 的二进制采用头、中、尾各 5 MiB 采样。具体边界以固定版本源码和测试为准。
- `src/lib/sync/operator_note.ts`：发送 `baseHash` 或缺失标记，维护待确认修改，并在 Ack 后推进记录。
- `src/lib/sync/operator_file.ts`：分片、上传会话、恢复与附件校验逻辑。
- `src/lib/sync/websocket_manager.ts`：消息分发、认证和冲突处理路径。
- `src/lib/sync/operator.ts`：批次同步、删除历史保留期保护及 UI 交互。
- `src/lib/storage/local_storage_manager.ts`：基线、pending、元数据依赖 Obsidian 本地存储。
- `src/main.ts`：生命周期与多个 manager 耦合，不能直接在 Node.js 中启动。

这些是源码证据，不是 headless 运行成功的证据。插件携带某字段也不代表所有服务端版本都执行对应保护。尤其附件、配置、重命名和删除的并发前置条件必须逐项确认。

本地相邻 Ops 仓库内有前期实验：`src/hermes_ops/fns_guard.py`、`fns_kanban.py`、`fns_sync_service.py`，以及被 Git 忽略的诊断与隔离拉取材料。它们不是已验收的实现，仅供当前工作区参考；不要复制真实笔记、凭据、备份或实验状态到本仓库。隔离拉取最终结果需在 Ops 侧重新核实，不能默认成功。

## 3. 建议架构

先添加明确接口，避免一开始重排全部上游文件。以下是设计名称，不代表现有 API：

| 边界 | 责任 |
| --- | --- |
| `VaultAdapter` | 安全路径、枚举、读写、stat、目录、删除、原子替换与变更监听 |
| `StateStore` | 基线、游标、pending、删除意图、上传会话、冲突及事务恢复 |
| `Transport` | 复用官方消息编码与连接行为，提供 Node.js WebSocket/HTTP 宿主适配 |
| `HostServices` | 时钟、定时器、日志、通知与需要人工决策的事件 |
| `ConflictResolver` | 生成冲突记录、获取解决结果、校验结果与版本有效性 |
| 服务入口 | 配置加载、单实例锁、启停、重试、健康状态、退出码 |

共享核心不应导入 Obsidian UI、DOM 或 Hermes。插件适配继续使用 Vault/App；Node 适配使用文件系统和持久化存储。上游中难以直接复用的函数应做小范围依赖注入，不要复制整个文件后长期平行修改。

文件监听只是变更提示，必须配合启动扫描与周期校验；网络断开期间保留本地操作。防止远端落盘引起监听回声，也不能用长时间忽略窗口吞掉真实本地修改。状态目录放在 Vault 外，避免内部记录被同步。

## 4. 同步与持久化约束

- 三方比较使用已确认共同基线、本地当前版本与远端当前版本。
- 首次接入时没有共同基线：同路径不同内容不能按时间戳自动覆盖；缺少文件不能直接解释为删除。
- 协议哈希严格兼容上游；本地快照和验收可以额外使用完整 SHA-256。采样哈希不能证明所有字节完全相同。
- 发送请求、认证成功、批次 End 或队列为空，单独都不能证明同步成功。按消息类型核对分页、请求数量、Ack、分片完成和持久化结果。
- 写入和删除前验证本地版本未变化；上传前使用协议支持的远端前置条件。没有条件写能力时，记录能力限制并保守处理，不能承诺消除所有竞态。
- 在确切版本未确认前，不推进共同基线。Ack 丢失时允许幂等重放或重新核对，不允许虚报成功。
- 删除需要持久化意图与历史；重命名包括大小写变化、跨目录及目标路径冲突。
- 单文件写入使用临时文件与原子替换；明确文件落盘与数据库事务间的崩溃恢复顺序。
- 限制并发、缓冲区、重试和日志量；支持大附件流式或分片处理。
- 防止 `..`、绝对路径、符号链接逃逸及大小写碰撞；内置状态和临时文件必须排除。
- 启动配置中区分笔记、附件和 Obsidian 配置同步。MVP 先覆盖笔记与附件；配置同步必须明确范围与排除规则后启用。

## 5. 智库馆长冲突处理契约

本客户端暴露通用契约，Hermes Ops 负责将任务分配给 `librarian`。AI 合并文本不是未经校验即可写回的授权。

建议冲突记录字段：`schemaVersion`、`conflictId`、`kind`、`path`、`base`、`local`、`remote`、`status`、`createdAt`。每个版本保存存在性、完整内容摘要、可用的协议版本信息与受控快照引用。路径和正文仅在受控存储中供解决者读取，不写普通服务日志。

建议生命周期：

```text
detected → awaiting-resolution → validating → applying → verified → resolved
                                  └─ versions changed → new conflict
```

1. 冲突首先持久化，并保留共同基线与双方内容；基线不存在时明确标记。
2. 通过稳定幂等键创建馆长任务；重启、重试不会创建重复任务。
3. 馆长输出结构化决策：合并内容、保留本地、保留远端或确认删除，并引用所处理的版本摘要。
4. 馆长不直接绕过客户端写共享 Vault。客户端验证任务归属、决策结构、内容与路径以及双方当前版本。
5. 新修改使旧决策失效时，创建新一轮冲突；不能用过期合并覆盖新内容。
6. 按协议提交解决结果，并通过 Ack 和内容核对后标记 `resolved`。
7. 附件不能可靠合并时，馆长负责保留双方、说明阻碍并提出选择或升级处理。任务保持未解决，不能伪造成功；既有知识库人工审批规则继续适用。

冲突应阻塞相关路径，其他独立路径尽量继续；若上游批次机制迫使 MVP 暂停整个 Vault，必须作为明确限制记录和测试。冲突不能悄悄切换为“较新者胜出”。
