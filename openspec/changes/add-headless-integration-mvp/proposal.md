## Why

目前仓库只有继承的 Obsidian 插件和 headless 交接方案，无法作为 Hermes 的独立同步客户端运行。首版需要在隔离环境证明笔记与附件双向同步、故障恢复和馆长冲突处理可行，同时保持上游协议实现的单一来源，使持续合并上游可验证、可维护。

## What Changes

- 以正式稳定版 `2.4.0` / `f2b15c09` 为客户端基线，复现并修复该版本的继承测试；保持插件构建与 lint 通过，建立模块复用清单、定点补丁清单和固定服务端版本的协议能力矩阵，不以 master/main 分支头为基线。
- 沿认证、笔记和附件下载的最小链路抽取宿主接口，提供 Node 适配；同一协议实现继续被原插件使用。
- 增加单 Vault 的只读、一次性双向同步和常驻运行入口，支持笔记与附件的新增、修改、删除、重命名以及必要的目录操作。
- 接入持久化操作、基线、上传会话、冲突和检查点；以版本校验、完整批次及持久化结果判定成功，支持断线与崩溃恢复。
- 将状态绑定到经验证的远端身份、远端 Vault 及本地目录身份；配置错配时拒绝恢复旧操作，不自动重新绑定或清空基线。
- 提供通用受控本地修改入口，使 Bot 修改与远端落盘共用覆盖版本复核、文件操作和状态提交的互斥边界；Ops 负责接入并限制绕过入口的写入。
- 保留上游协议哈希，完整摘要用于本地版本、快照、冲突和操作确认。按用户 2026-09-16 决策，大附件采样盲区作为首版已知上游限制，等待上游正式版本修复；本 change 不实施专项补丁、强制上传或周期盲区审计，该场景不再阻塞首版交付。
- 提供通用冲突查询与决策提交接口，用确定性 resolver 验证，再由外部 Hermes Ops 完成馆长集成。
- 增加合成数据、固定服务端、实际 Obsidian 插件与 Node 客户端的隔离验收；记录成功回执、完整内容清单和明确的能力限制。
- 首版不包含生产切换、多 Vault 调度、配置同步、云预览、分享、管理界面或客户端内置 AI；不改造服务端协议。

## Capabilities

### New Capabilities

- `upstream-compatible-core`: 共享协议行为、窄宿主接口及可持续上游合并的验证契约。
- `headless-sync-runtime`: 单 Vault 的 Node 运行入口、只读与双向操作、扫描、文件系统和资源边界。
- `durable-sync-state`: 操作持久化、版本关联、确认与检查点以及故障恢复。
- `versioned-conflict-resolution`: 三方冲突记录、幂等决策提交、版本复核和通用外部解决接口。
- `isolated-integration-acceptance`: 固定版本的协议验证、插件互操作和 Hermes 隔离验收标准。

### Modified Capabilities

无。当前没有已有主规格。

## Impact

- 预计影响 `src/lib/sync/`、`src/lib/storage/`、`src/lib/utils/` 和插件装配入口；抽取范围由实际复用清单决定，避免整体移动文件和复制 operator 实现。
- 新增 Node 宿主、持久化实现、CLI、协议与恢复测试，以及中文使用和兼容性文档。数据库、文件锁和 Node 网络适配依赖在基线阶段验证后确定，不升级无关依赖。
- 上游同步、通用修复、接口抽取和 headless 功能分开提交；原插件仍需通过回归验证。
- Hermes Ops 只作为外部集成依赖，本变更不编辑该仓库，不使用生产凭据，不执行发布或生产部署。馆长验收未完成时仅能声明客户端测试通过，不能声明完整首版验收通过。
- Ops 隔离验收仍需验证 Bot 受控写入及声明支持范围内的双向往返。大附件采样盲区专项三端验收延后，报告明确该范围未获收敛保证；保留既有失败证据，不标记已修复或已通过。此项例外不豁免其他确认、冲突及数据完整性要求。
