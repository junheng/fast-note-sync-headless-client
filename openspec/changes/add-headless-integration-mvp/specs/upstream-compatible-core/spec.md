## Purpose

使 Node 客户端与原 Obsidian 插件持续遵循同一上游协议行为，并通过可追溯的差异记录和双宿主回归证明兼容性，避免首版完成后形成无法持续合并上游的独立协议分支。

## ADDED Requirements

### Requirement: 协议行为保持兼容

两种宿主 SHALL 对支持的相同输入遵循一致的消息字段、序列化、协议哈希、分页和附件分片语义；每个声明支持的服务端版本 MUST 有明确的能力和验证证据。

#### Scenario: 跨宿主协议向量一致
- **WHEN** 两种宿主处理相同的中文、emoji、空笔记和跨越 10 MiB 边界的附件向量
- **THEN** 协议哈希和消息语义与固定上游基线一致，宿主运行信息差异被显式排除

#### Scenario: 未确认的服务端能力
- **WHEN** 某服务端的操作前置条件或确认语义没有验证证据
- **THEN** 客户端报告该能力未验证，不将认证成功视为兼容性证明，也不执行依赖该能力的风险写入

#### Scenario: 同协议哈希对应不同完整内容

- **WHEN** 两个附件的协议采样输入相同但完整内容不同
- **THEN** 两种宿主继续使用共享的上游协议哈希实现；headless 的完整摘要不替换线上的哈希字段；将已复现的大附件采样盲区保留为已知上游限制，专项修复等待上游正式稳定版，不以该限制暂停整个首版实施或声称该场景已收敛

### Requirement: 上游复用可追溯

每个候选版本 SHALL 提供模块复用和定点补丁记录，标明原样使用、宿主抽取、通用修复或产品策略差异及对应回归；协议行为 MUST 保持单一实现来源，不得通过复制 operator 或完整模拟 Obsidian 来形成平行实现。

#### Scenario: 评审一处宿主抽取
- **WHEN** 评审从上游同步流程抽取的宿主依赖
- **THEN** 可以定位原始模块、抽取原因、两端调用位置和对应测试，并确认没有第二份相同协议实现

### Requirement: 上游合并保留双宿主回归

客户端基线和常规升级 SHALL 选择已发布、非草稿、非预发布的正式稳定 release，并记录 tag 及精确提交，MUST NOT 以 master/main 分支头或仅凭 package 版本号选定基线。未发布的必要修复必须独立 backport，记录来源、理由和回归。合并上游后 SHALL 验证插件构建、继承测试及 headless 协议和恢复测试；失败 MUST 区分既有基线与本次回归，不能静默跳过后声明合并完成。

#### Scenario: 分支头与正式版本的包版本号相同

- **WHEN** 开发分支和正式 release 都声明 `2.4.0`，但提交不同
- **THEN** 选择正式 release tag 的精确提交，分支头仅用于观察，不自动成为开发基线

#### Scenario: 上游修改 Ack 或分片行为
- **WHEN** 上游合并涉及确认消息或附件传输
- **THEN** 两种宿主的相关兼容测试及 headless 故障恢复测试通过后，才能更新已验证基线
