## Context

动机和范围见 [proposal.md](proposal.md)。现有代码仍以 `FastSync` 插件对象组织流程，`operator_note.ts`、`operator_file.ts` 和 `operator.ts` 同时引用协议行为、Vault、存储和 UI。当前 headless 能力尚未实现。

用户明确要求以正式稳定版而非开发分支头为基础。当前选择 `2.4.0` / `f2b15c09d34e621d2d97ad526fdee03460bac151`，在 `headless/stable-2.4.0` 上移植项目准备文档，保留原分支历史。固定 Node 24.14.0 / pnpm 11.1.2 初次重跑时，auth 和 mirror 仍失败，build、lint 与 vault-name 测试通过。准备阶段 `1bfb4069` 上的翻译键和 lint 失败仅作历史记录，不移植这些开发分支改动。`BASELINE.json` 记录客户端稳定基线及候选服务端的有界探测范围，没有完整运行兼容性证明。

以下抽取风险已在源码检查中识别，尚未作运行故障复现；正式抽取前须在稳定版对应源码重新核对：

- `LocalStorageManager.savePending` 捕获持久化异常后继续；Node 写操作需要可传播失败的持久化边界。
- `receiveNoteModifyAck` 从当前按路径保存的 pending 取哈希；新版本需要保护具体发送版本，不能让旧确认提交新编辑。
- `receiveFileSyncUpdate` 和 `receiveFileSyncEnd` 中存在在完整落盘前更新同步时间的路径。
- `receiveNoteSyncRename` 存在先删除已占用目标的路径，需要在实际修改前接入冲突检查。

这些证据决定扩展点的位置，不构成全面的上游缺陷结论；复用清单见 `docs/headless/REUSE.md`。

实施进展：稳定版 auth/mirror 已修复并通过完整插件回归。候选服务端正式版 `3.6.1` / `7a6c7879` 已用固定摘要镜像完成有界附件探测：同协议哈希异内容在 WS 上传检查中返回无需更新，完整读回仍是旧内容；REST 对照可存储不同内容，但不证明原子条件写。详见 `docs/headless/SERVER-CAPABILITIES.md`。用户于 2026-09-16 明确决定暂不处理此问题，等待上游修复：将大附件采样盲区移出首版必需验收范围，保留已知限制和探测证据，恢复其他任务。该决定不授权修改服务端，也不免除其他数据完整性要求。

## Goals / Non-Goals

**Goals:**

- 一个共享的协议实现，同时由插件和 Node 宿主实际执行。
- 每次抽取沿可运行链路推进，使补丁可以独立评审并继续合并上游。
- 用明确的持久化生命周期包围现有操作，证明发送、确认、落盘和检查点之间的恢复行为。
- 首版以单 Vault、有限并发和必要时整批暂停换取可验证性。

**Non-Goals:**

- 不整体重写同步调度器，不复制 operator 为 Node 专用版本，不为兼容旧签名实现完整假 Obsidian。
- 不把所有原插件设置搬到 headless，不复刻插件 UI 或普通日志中的私人路径。
- 不承诺客户端能够补足服务端缺失的条件写能力；风险操作必须按能力矩阵保守阻塞。

## Decisions

### 1. 从真实调用链抽取宿主依赖

优先保持上游文件布局。先让认证、笔记下载、附件下载在 Node 运行，再扩展写路径。接口名称为设计名称，实际成员依据消费者收敛：

| 边界 | 责任 | 上游复用方式 |
| --- | --- | --- |
| `VaultAdapter` | 枚举、版本化读取、范围读取、原子替换、重命名、删除及安全路径 | 在实际 I/O 位置替换 Vault 调用；协议流程共用 |
| `StateStore` | 操作、基线、游标、会话、冲突和事务 | 替换持久化访问；Node 失败必须传播到调度 |
| `Transport` | WebSocket/HTTP 宿主 I/O、取消和连接标识 | 编解码、认证、消息字段和分片行为保持单一来源 |
| `HostServices` | 时钟、调度、日志、通知和宿主事件 | Node 提供无 UI 实现，插件保留 UI 适配 |
| 冲突策略边界 | 写入前检查、保存冲突、提交决策 | 通过生命周期接入；Hermes 不进入共享模块 |

不把以上接口简单包装成包含所有插件属性的新巨型对象。每增加成员都记录消费者和测试。纯算法仍引用同一实现，浏览器定时器或范围读取属于宿主适配。

备选的两套协议实现会使上游修复无法自动进入 Node；完整插件模拟层又会把 UI 生命周期带入服务，因此不采用。通用正确性修复与 headless 策略差异分开提交，避免同步代码中散布 `if (headless)`。

### 2. 先建立能力矩阵，再开放写入

第一阶段逐操作记录：消息与响应、内容版本字段、前置条件、Ack 关联能力、分页结束语义、删除历史保留和失败恢复方式。额外验证服务/主体/Vault 的身份核对能力、同协议哈希异内容的传输行为、远端完整内容证据和实际读回能力。源码参考与实际服务端用例分列。

服务端支持的条件写直接复用。没有充分并发保护的操作在可能覆盖未知版本时进入 `blocked-capability`，保留意图和快照。写前读取不被视为原子条件写；不自动升级或修改服务端。若声明范围内的首版必需操作在目标服务端无法安全通过验收，报告版本目标受阻并重新评审兼容范围，不能把阻塞降级为成功。大附件采样盲区为用户已明确接受的范围例外，按第 8 节处理，不再据此暂停整个 apply。

此规则已固定，待验证的是目标服务端事实，因此实现可以先开展基线和只读任务。

### 3. 可靠性通过操作生命周期接入共享流程

在上游流程的发送前、响应处理、文件应用和批次完成位置抽取窄扩展点，形成 Node 的持久化生命周期。不得仅在外围包一层日志而让原有提前推进游标的路径绕过它。

```text
observe --> persist-intent --> send/apply --> verify --> commit
                 |                |            |
                 +------------> recover <-------+
                                  |
                             revalidate
                                  |
                        retry / conflict / block
```

逻辑记录包括：`binding`、`operations`（本地操作标识、路径、类型、基线、发送快照、连接标识和状态）、`baselines`、`batches`/`pages`、`transferSessions`、`conflicts` 和 `decisions`。快照位于 Vault 外，以完整摘要校验；大内容不要求直接存入数据库。

`binding` 保存规范化端点、经验证的非秘密服务身份及认证主体、远端 Vault 标识、本地规范路径和目录身份，以及格式版本。本地目录身份须能识别同路径替换，不能仅存路径字符串。凭据值及其摘要不进入绑定；同主体令牌轮换应正常恢复。目录或端点迁移不自动视为等价目标，首版返回 `state-identity-mismatch`，保留原状态，由独立的显式重新接入流程处理，不能自动清空或改绑。

启动先检查配置和本地目录绑定，再进行仅用于身份验证的认证/查询。在远端绑定验证前，不恢复旧 pending、不采用旧游标、不应用推送文件；提前到达的事件必须有界隔离，不能进入恢复流程。每次重连重新验证，远端身份无法取得或验证时返回 `state-identity-unverified`。服务端升级后的版本兼容检查与逻辑身份核对分开；同一服务和 Vault 的版本升级不必然代表目标变化，但仍需通过能力门禁。

持久化实现采用事务存储边界，数据库驱动在固定 Node 环境下验证后选择；优先评估嵌入式事务数据库，不把继承的分散 localStorage 写入直接映射成多个无事务 JSON 文件。格式从第一版带 `schemaVersion`，损坏或未知格式拒绝自动重建。

发送内容从不可变快照取得，同路径首版最多一个在途修改。新的本地编辑进入后继操作。应用 Ack 时只提交对应发送版本；连接标识仅能过滤旧连接，不能创造服务端没有的操作标识。无法关联时重新读取远端核对，禁止拿当前 pending 猜测。

下载和临时内容准备可以在互斥区外完成。实际文件应用顺序为：取得本地变更互斥权、读取当前版本并复核预期条件、持久化意图及恢复所需原版本、原子替换和必要的落盘同步、事务提交完成状态、释放互斥权。删除和重命名遵循相同生命周期，重命名同时保护来源与目标。重启按原/目标摘要识别已应用、未应用或外部修改；失败不会自动清空状态。首版使用 Vault 级本地变更互斥，减少多路径死锁及目录操作竞态；网络传输不占用该互斥权。

数据库事务不能包住文件系统替换，因此仍需上述恢复记录。Bot 不直接取得写锁后自行改文件，而是向状态所有者提交通用本地修改请求：`requestId`、`operation`、相对路径、预期完整版本或不存在条件，以及受控内容输入；重命名包含目标条件。同一所有者串行处理 Bot 请求、远端落盘和冲突解决，互斥覆盖复核到状态提交的完整窗口。请求幂等结果与恢复记录绑定；返回本地提交完成不等于远端同步成功。

本仓库负责受控入口、权限检查、版本条件、幂等和恢复；Hermes Ops 负责让 Bot 使用入口，并以不同权限身份或等价强制限制禁止其直接写 Vault。启动必须声明 `controlled` 或 `exclusive` 本地写入方式：前者用于已配置隔离权限的协作接入，后者只用于排他访问的隔离目录，包括只读拉取。声明不是权限有效的证明，Ops 验收必须实际尝试绕过写入；未声明方式则返回 `local-writer-contract-required`，不应用文件。仅能轮询发现绕过的方案不足以通过验收；任意同权限进程或管理员绕过仍属于不受支持运行方式，不能声称软件互斥覆盖了它们。

### 4. 检查点和成功状态独立于进度展示

记录远端观察到的游标与已经提交的安全检查点。页面和批次只有在操作确认、附件校验、落盘及状态提交完成后才满足成功条件。

首版选择保守的批次检查点：存在未完成、冲突或失败时不推进该批次安全检查点，已完成项持久化以支持幂等重放。暂不引入带任意缺口的复杂检查点算法。冲突可暂停整个 Vault 批次，状态明确指出阻塞范围。UI 已处理数量不能作为 Node 成功判定。

### 5. 从扫描推导变更，但不从缺失直接推导删除

启动与周期扫描是核对依据，监听只是加速提示。扫描失败不修改已确认清单；本地删除意图必须依据可靠事件或成功完整扫描与已确认基线核对后持久化。无基线、历史过期、目录不可访问或挂载异常均进入重新核对状态。

远端写入使用具体操作和内容版本抑制回声，避免沿用长时间忽略窗口吞掉本地编辑。重命名锁定并复核来源和目标；离线无法可靠识别重命名时按受保护的新建及删除意图处理，不能先删来源再假定目标上传成功。

Vault 及状态目录均有所有权保护，防止不同状态目录的进程同时写同一 Vault。首版对同步树中的符号链接采取拒绝策略，并测试目录替换导致的路径竞态。状态目录必须在 Vault 外；临时落盘文件采用明确排除规则。

### 6. 首版冲突接口采用本地通用契约

冲突记录和决策字段见对应规格。首版通过 CLI 暴露冲突列表、受控详情和 JSON 决策提交，常驻模式复用同一处理逻辑；进程所有者串行应用决策，辅助提交命令不能直接修改 Vault 或绕过状态所有权。具体 IPC 实现和命令拼写在接口实现时确定。

本地文件权限限制详情和提交入口；普通状态只包含计数、标识和脱敏原因，不输出正文。相同幂等标识的不同载荷拒绝。决策应用前重新核对双方版本，确认后才标记 `resolved`。

冲突决策的本地复核和应用必须进入第 3 节的同一互斥区，不能另外建立只在冲突模块内部有效的锁。远端版本复核仍依赖服务端前置条件，不把本地互斥解释为远端条件写。Bot 本地修改与冲突决策可共用进程通信及幂等基础，但保留不同操作语义。

先使用确定性 resolver 验证；Hermes Ops 负责把任务交给馆长并调用契约。首版不部署开放网络 API，避免为隔离验收引入额外服务和鉴权系统。

### 7. 双层测试证据和维护记录

可控协议测试替身用于重复、乱序、断线及故障注入；固定实际服务端用于验证替身没有虚构协议能力。实际 Obsidian 插件与 Node 客户端验证宿主互操作，Hermes 集成另有业务回执。四类结果分别记录。

复用清单记录源模块、宿主依赖、抽取点、通用补丁、上游是否已吸收及测试。上游升级只选择正式稳定 release tag 并记录精确提交，不合并开发分支头。每次升级重新验证两端，并移除已经被上游取代的自定义补丁。未发布但必要的修复作为独立 backport 记录来源、理由和回归。上游同步、通用修复、接口抽取、headless 功能独立提交；不启用继承发布工作流作为验收手段。

### 8. 协议哈希兼容与已接受的上游限制

协议哈希继续调用上游同一实现，完整 SHA-256 用于本地版本、不可变快照、基线、冲突复核和声明范围内的验收，不替换线上字段。保留启动/周期本地扫描和正常操作的内容核对，避免额外引入与上游无关的漏检或错误确认。

已复现的 20 MiB / 偏移 6 MiB 合成向量保留为哈希兼容性特征和上游升级后的复核依据。用户 2026-09-16 决定等待上游修复，因此本 change 不新增采样盲区专用上传/确认机制、REST 绕行、协议字段修改、静默远端变化的专项周期审计或插件/服务端补丁；三端盲区收敛验收延后。此限制影响大附件中未反映到协议采样哈希的修改，不取消一般附件同步。

首版支持声明和验收报告必须列明该限制，不能声称已修复、已通过盲区用例或已完成持续全内容审计。已经观察到的内容差异、未完成操作和冲突仍按普通版本保护机制保留，不能为解除项目阻塞而清除 pending 或把明确失败改报成功；该限制本身不禁止启动或继续开发其他功能。

上游正式稳定版包含相关修复后，再复核原向量、完整内容、插件与 Node 三端结果，并决定是否恢复相应专项任务。本 change 不承诺上游的修复时间，也不创建服务端兼容修复 change。

## Risks / Trade-offs

- [服务端缺少必要的版本前置条件] → 能力矩阵提前暴露；安全阻塞，必要时重新评审首版兼容范围，不重写服务端。
- [接口抽取逐渐变成巨型插件替身] → 每个成员绑定真实消费者，按只读纵向链路验证，记录补丁规模和复用关系。
- [旧 Ack 与新编辑混淆] → 不可变发送快照、同路径串行、连接隔离和远端核对；不能关联时不提交。
- [冲突阻塞全 Vault] → 首版明确采用保守批次检查点；状态展示阻塞范围，路径级继续同步后置。
- [外部 Bot 写入与原子替换竞态] → 受控入口和 Ops 权限隔离；用复核后/替换前屏障验证互斥，用绕过写入测试验证权限，缺少接入条件不通过验收。
- [复用旧状态连接了不同目标] → 启动和重连验证非秘密身份绑定，错配或无法验证时拒绝恢复，不自动清空或改绑。
- [采样哈希未反映实际内容变化] → 用户已接受为首版已知上游限制，专项修复/审计/三端验收延后；保留证据，等待正式稳定版修复，不再作为整个 apply 或首版声明范围的阻塞项。
- [大附件与保留快照消耗磁盘] → 配额、磁盘不足测试和有界 I/O；未解决快照不得自动清理，空间不足则阻塞。
- [外部 Hermes 尚未就绪] → 保持业务验收任务未完成，可交付客户端测试证据，不虚报完整首版完成。

## Migration Plan

1. 在固定运行时复现基线，以独立补丁修复后记录提交；不迁移生产数据或继承其他客户端状态。
2. 以全新隔离 Vault 和外置状态目录运行只读，在身份绑定和本地写入方式通过校验后开放文件应用，再在同一已验证状态格式上开放双向；模式切换需重新核对本地与远端版本。端点、主体、远端 Vault 或本地目录身份改变时拒绝旧状态恢复，目录迁移或改绑须单独显式处理。
3. 逐阶段加入恢复、冲突和运行入口，始终运行插件回归；候选产物只用于隔离验收。
4. 状态格式变更提供显式迁移及备份验证；旧二进制遇到未知格式拒绝启动。隔离回退保留快照，使用新的测试目录重建，不恢复旧游标后盲目重放删除。
5. Ops 侧独立完成馆长验收。生产发布、备份与切换另立部署任务，本变更不执行。
